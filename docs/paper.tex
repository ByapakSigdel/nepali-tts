\title{An Offline Multi-Speaker Nepali Text-to-Speech System on Consumer Hardware}

\author{\IEEEauthorblockN{Byapak Sigdel}
\IEEEauthorblockA{Independent Research \\
\texttt{github.com/ByapakSigdel/nepali-tts}}}

\maketitle

\begin{abstract}
We present a fully offline, multi-speaker Nepali (Devanagari) text-to-speech (TTS) system built entirely
from public data and trained on a single consumer 8\,GB laptop GPU. The system fine-tunes a VITS model
(via \emph{piper1-gpl}) from an English warm-start checkpoint, uses espeak-ng for Nepali
grapheme-to-phoneme (G2P) conversion, and exports to ONNX for dependency-light offline inference. Beyond the
model, we document a reproducible engineering recipe for training on a brand-new NVIDIA Blackwell
(\texttt{sm\_120}) laptop GPU under WSL2 with PyTorch~2.11 --- a configuration with several currently
undocumented failure modes. On approximately 3.8 hours of curated speech from 20 speakers, the generator loss
drops sharply and then plateaus near 31 (typical of VITS) while perceptual quality keeps improving, and the
model produces increasingly intelligible Nepali across multiple selectable voices. To pool more compute
without leaving the consumer/free tier, we contribute a fault-tolerant \emph{checkpoint-relay} that joins the
laptop with free, preemptible cloud GPUs into a single training run through a Hugging Face Hub ``baton'',
whose coordination layer we harden using a large-scale adversarial (multi-agent) code review; we further
analyze when low-communication parallel training (DiLoCo) is---and is not---worthwhile for a near-converged
GAN on small data, and report an ASR round-trip intelligibility (CER) measurement. All code, configuration,
and a clean-machine reproduction guide are released.
\end{abstract}

\section{Introduction}
Nepali is a low-resource language for speech technology. High-quality TTS typically assumes (a) large clean
single-speaker corpora, (b) datacenter GPUs, and (c) online inference. We target the opposite regime:
\emph{public multi-speaker data, a single 8\,GB laptop GPU, and fully offline deployment}.

Our contributions are: (1) an end-to-end reproducible pipeline (data $\rightarrow$ preprocessing
$\rightarrow$ training $\rightarrow$ ONNX) for multi-speaker Nepali TTS; (2) a Nepali text frontend built on
espeak-ng with an empirical G2P accuracy analysis; (3) a documented engineering recipe for VITS training on
Blackwell\,+\,WSL2\,+\,PyTorch-2.11, which was the primary practical obstacle; (4) a fault-tolerant
\emph{checkpoint-relay} (Section~\ref{sec:relay}) that pools the laptop with free, preemptible cloud GPUs
into one training run, with a coordination layer hardened by adversarial review, plus an honest analysis of
when low-communication parallel training (DiLoCo) pays off in this regime; and (5) full release of all
artifacts.

\section{Background and Components}
\textbf{VITS}~\cite{vits} is an end-to-end TTS model combining a conditional variational autoencoder,
normalizing flows, and adversarial training; it jointly learns acoustic representations and a HiFi-GAN-style
vocoder, supports multiple speakers via a learned speaker embedding, and reaches strong naturalness.
\textbf{Piper / piper1-gpl}~\cite{piper} is a lightweight VITS training and ONNX-inference toolkit aimed at
fast offline TTS; it provides espeak-ng phonemization and multi-speaker support.
\textbf{MMS-TTS}~\cite{mms} (\texttt{facebook/mms-tts-npl}) is a pretrained single-speaker Nepali VITS used
here as a baseline. \textbf{espeak-ng} is a rule-based multilingual phonemizer with a Nepali (\texttt{ne})
voice, used as our G2P frontend.

\section{Data}
We use public OpenSLR corpora (Table~\ref{tab:data}). The current \emph{Stage~A} corpus comprises 2{,}739
clips ($\sim$3.8 hours) from 20 speakers, resampled to 22.05\,kHz mono, peak-normalized, and silence-trimmed.
The corpus is heavily imbalanced (Fig.~\ref{fig:speakers}): the largest speaker contributes 566 clips, the
median about 60, and only one male speaker (109 clips) is present. Multi-speaker training shares phonetic
learning across all speakers, which mitigates but does not eliminate scarcity for data-poor voices.

\subsection{Architecture}
We train a multi-speaker VITS model: the generator (SynthesizerTrn) has $\approx$30\,M parameters and the
multi-period discriminator $\approx$47\,M. A learned speaker embedding conditions the generator; voices are
selected at inference by integer speaker id.

\subsection{Nepali Text Frontend}
Devanagari text is converted to phonemes by espeak-ng (\texttt{ne}), a phoneme inventory of 256 symbols.
This handles consonant conjuncts, schwa, and numeral expansion natively (Section~\ref{sec:g2p}). Heavier
text normalization and a correction lexicon are left to future work.

\subsection{Warm-Start Transfer}
With only $\sim$3.8 hours of data, training from scratch is impractical on one GPU. We warm-start the vocoder
from the English \texttt{en\_US-lessac-medium} checkpoint: because VITS uses a shared IPA-based phoneme
inventory, the language-agnostic vocoder transfers while the model adapts to Nepali phonetics and speaker
identities. A full encoder/flow warm-start is blocked by the single$\rightarrow$multi-speaker architecture
mismatch and is future work.

\subsection{Offline Export}
Trained checkpoints are exported to ONNX (legacy exporter) and run via \texttt{onnxruntime} on CPU --- no GPU
or network required at inference. This is the deployable artifact. For the exported model we optionally average
the generator weights across several late-plateau checkpoints (a model-soup / stochastic-weight-averaging style
average); applied only to the inference artifact and never fed back into optimization, this is a zero-risk way
to obtain a slightly smoother voice.

\subsection{Deployment: Offline Web Frontend}
For interactive use we provide a Gradio web application (\texttt{frontend/app.py}). The user enters Nepali
text, selects one of the 20 speaker voices, optionally adjusts speed and variation, and receives audio. The
app loads the exported ONNX model, runs \texttt{onnxruntime} on CPU, and serves a browser UI on
\texttt{localhost} --- entirely offline; under WSL2 it is reachable from the Windows browser via
\texttt{localhost} forwarding. It re-exports the latest checkpoint on launch, so the served voice tracks
training progress. The app also accepts \emph{romanized} (Latin-script) Nepali and code-mixed English
(e.g.\ ``\textit{kasto cha tapaiko aaile}''): an offline rule transliterator
(\texttt{indic-transliteration}/OPTITRANS plus a curated Nepali word and phonetic-normalization map) converts
input to Devanagari, shown in an editable preview so the user can correct the residual errors of deterministic
transliteration before synthesis (Section~\ref{sec:future}).

\section{Distributed Training on Consumer and Free Cloud Compute}
\label{sec:relay}
A single 8\,GB laptop is the binding constraint. We add an \emph{optional} way to pool the laptop with free,
preemptible cloud GPUs (Google Colab) \emph{without} datacenter infrastructure, while preserving a hard
requirement: training progress must never be lost.

\subsection{Checkpoint-Relay (the ``baton'')}
True synchronous data parallelism (DDP) is infeasible here: the laptop (home network) and a cloud VM would
exchange gradients every step over high-latency, low-bandwidth links, orders of magnitude slower than a single
GPU. Instead we observe that VITS already checkpoints frequently for fault tolerance, and we lift that
checkpoint into a \emph{relay}: one machine trains at a time and passes the full-state checkpoint (weights,
optimizer, epoch, step) to the next through a private Hugging Face Hub repository (Fig.~\ref{fig:relay}). This
pools the two GPUs' wall-clock \emph{hours} into one continuous run---the cloud trains a shift while the laptop
rests, and vice versa.

Correctness rests on three invariants enforced by a small coordination layer (\texttt{hf\_sync.py}):
(i)~a compare-and-set \emph{lock} with an independent heartbeat ensures the machines take turns and never train
simultaneously; (ii)~each handoff is a single \emph{atomic} multi-file commit (checkpoint $+$ an epoch marker
$+$ the speaker/phoneme config), so the metadata can never disagree with the bytes; and (iii)~a push-side
\emph{epoch guard} refuses to upload a checkpoint older than the one already in the cloud. Invariant~(iii) is
the linchpin: even if the lock failed and both machines trained at once, neither could overwrite the other's
newer work---the worst case degrades from \emph{lost progress} to merely \emph{wasted compute}.

\centering
\includegraphics[width=\columnwidth]{relay.png}
\caption{Fault-tolerant checkpoint-relay. The full-state checkpoint is a ``baton'' passed through a private
Hugging Face Hub repo; a lock enforces turn-taking and an epoch-guard forbids overwriting newer work.}
\label{fig:relay}
\end{figure}

\subsection{Hardening by Adversarial Review}
Because the relay underwrites a ``no progress lost'' guarantee, we stress-tested it with a large-scale
multi-agent code review (dozens of independent reviewer and adversarial-verifier passes). It surfaced several
real, subtle hazards---e.g.\ a slow multi-hundred-MB upload starving the lock heartbeat (letting the peer
reclaim a \emph{live} lock), fail-\emph{open} reads treating a transient network error as ``lock free'', and
non-atomic checkpoint/metadata writes---each of which could have caused silent double-training or an
older-over-newer overwrite. All were fixed (independent heartbeat, fail-\emph{closed} reads, atomic commits,
the epoch guard above) and the hardened layer was re-validated against the live repository.

\subsection{When is Parallel Training Worthwhile? A DiLoCo Analysis}
For genuine concurrency one can use \emph{low-communication} parallelism: DiLoCo~\cite{diloco}, in which each
worker trains independently for hundreds of inner steps and the workers periodically average a parameter-space
``outer gradient'', communicating only every $H$ steps and thus tolerating WAN links. We analyzed it for our
setting and reach an honest negative result. First, the relay already pools both GPUs' hours, so DiLoCo's
\emph{only} marginal gain is concurrency---capped at $2\times$ for two workers and eroded by per-round sync over
a slow uplink and by cloud preemption to an estimated $1.3$--$1.6\times$. Second, VITS is adversarial:
periodically averaging two independently-drifted generators \emph{and} discriminators across machines is
unproven and risks the min-max balance, and our run is already past its loss plateau, so the quality at stake
is large relative to the few hours saved. We therefore reserve DiLoCo for the much larger Stage~B corpus---a
long, large-data run that fits its regime---and, when run, gate it on the objective metric below with automatic
fallback to the relay, so the ``no progress lost'' requirement always holds. The full design is released for
that future work.

\section{Results}
\subsection{Training Dynamics}
Figure~\ref{fig:losses} shows the generator (\texttt{loss\_g}) and discriminator (\texttt{loss\_d}) losses,
merged across all runs by training step. The generator loss falls sharply (47 $\rightarrow$ 37) within the
first few hundred steps as the warm-start adapts, then settles into the $\approx$31--33 range and plateaus
from step $\approx$27k (epoch~21) onward, holding flat as training continued toward a 350-epoch target ---
expected for VITS, whose aggregate loss saturates while perceptual
quality (driven by the adversarial and mel terms) keeps improving, as the mel-spectrograms in
Fig.~\ref{fig:mel} show. The discriminator loss remains balanced at $\approx$2.7 --- a stable adversarial
equilibrium with no mode collapse or discriminator runaway.

\subsection{Objective Intelligibility (ASR Round-Trip CER)}
We measure intelligibility by ASR round-trip Character Error Rate (CER): synthesize a fixed 15-sentence Nepali
test set, transcribe the audio with a Nepali ASR (Whisper-large-v3), and compute CER against the input text
(lower is better). At epoch~$\approx$267 the current model scores CER~$=43.6\%$ (speaker~0). This number must
be read carefully: it conflates TTS error with the ASR's own substantial error on low-resource Nepali.
Inspecting the transcripts, the synthesizer in fact produces clearly recognizable Nepali---e.g.\ the input
``\textit{pani parekole bato chiplo bhayo}'' returns as ``\textit{pali parikule baito chipto bhayo}'', close,
with the recognizer fumbling fine detail---so the absolute value is inflated by the recognizer. CER is thus
most reliable here as a \emph{relative} regression tripwire (and as the automatic quality gate for the
distributed experiment of Section~\ref{sec:relay}). An absolute figure requires an ASR noise-floor
calibration---running the same recognizer on the natural recordings to subtract its own error---which we
identify as immediate future work. The harness is implemented and released.

\section{Limitations and Future Work}
\label{sec:future}
The reported numbers are mid-training; quality and CER will improve. The corpus is small ($\sim$3.8\,h),
female-heavy, and has a single male voice; Stage~B (SLR54, $\sim$157k utterances) is expected to be the
largest quality lever. Planned work includes a Nepali normalization and correction lexicon (nasalization,
loanwords, dates, currency) and a deeper (encoder/flow) warm-start.

A second direction is \emph{input flexibility and code-switched naturalness}. Many Nepali speakers type in
Latin script (informal romanized Nepali) and freely mix English words, e.g.\ ``\textit{hello sanchai
hunuhuncha tapai}''. The frontend now transliterates informal romanized Nepali to Devanagari and handles
code-mixed Nepali-English tokens via a fully-offline rule transliterator, so users need not type Devanagari.
This is deliberately conservative: deterministic transliteration of orthography-free romanized Nepali tops out
near 80\% word accuracy (mitigated by the editable preview), and embedded English is rendered with a nativized
Nepali accent; replacing the rules with a small neural transliterator is a clean offline upgrade. Beyond
input, producing a genuinely natural, casually code-switched \emph{voice} (mirroring real Nepali-English
speech) is a modeling and data problem: it requires code-mixed training data and consistent phoneme handling
for embedded English words --- a longer-term research phase.

Finally, expressive/emotional TTS remains a separate phase, requiring emotion-labeled data that no public
Nepali corpus currently provides.

\section{Conclusion}
A reproducible, fully offline multi-speaker Nepali TTS system is achievable from public data on a single
8\,GB laptop GPU---and, when more compute is wanted, by pooling that laptop with free, preemptible cloud GPUs
through a fault-tolerant relay that provably never loses progress, still without datacenter infrastructure.
The principal obstacle is not modeling but toolchain and systems engineering on brand-new hardware, which we
document so others can reproduce it. Training is healthy and ongoing (epoch~$\approx$267 of a 350 target); the
pipeline, data, recipe, and distributed-training layer are released in full.

\section{Reproducible Recipe: Blackwell (\texttt{sm\_120}) + WSL2 + PyTorch 2.11}
\label{app:recipe}

\textbf{Why WSL2, not native Windows.} The host is a Windows laptop, yet we train inside WSL2 (a real Linux
kernel) rather than natively. The deciding factor is the training \emph{toolchain}, not the GPU:
\texttt{piper1-gpl} compiles Cython/C extensions (notably \texttt{monotonic\_align}) via
\texttt{setup.py build\_ext}, a one-line \texttt{gcc} build on Linux but fragile on Windows (it requires the
MSVC toolchain and frequently fails); \texttt{espeak-ng}, the audio stack (soundfile/torchaudio/FLAC), and the
entire shell-based pipeline (download, preprocessing, the auto-resume loop, the relay) are Linux-first. WSL2
provides CUDA pass-through at near-native GPU throughput, so the Linux toolchain costs no speed. The trade-off
is a thin Windows$\leftrightarrow$Linux seam (path translation, \texttt{localhost} forwarding to reach the web
app from the Windows browser, and the WSL-specific CUDA quirks below); native Windows would instead pay the
heavier price of building those C extensions and porting the pipeline. Note also that training is driven by
background \emph{scripts}, not a notebook: a multi-day unattended run must survive disconnects, crashes, and
reboots, which a browser-bound Jupyter kernel does not---interactive notebooks are reserved here for the
cloud-GPU relay (Section~\ref{sec:relay}) and the web frontend, where interactivity actually helps.

These failure modes are largely undocumented as of writing.
(1)~VITS's \texttt{@torch.jit.script} fused op crashes in the TorchScript interpreter on \texttt{sm\_120}
(mis-reported as a 20\,MiB OOM); set \texttt{PYTORCH\_JIT=0}.
(2)~\texttt{expandable\_segments:True} uses CUDA virtual-memory APIs unsupported under WSL2, causing a
spurious ``16 billion GB in use'' OOM; do not set it.
(3)~Precision: \texttt{bf16} crashes (cuFFT cannot STFT \texttt{bf16}); \texttt{fp16} uses an unstable
experimental ComplexHalf FFT; use \texttt{fp32}.
(4)~Intermittent backward-pass ``CUDA error: unknown error'' at random steps is a known \texttt{sm\_120}
driver fault; updating the driver ($596.36 \rightarrow 610.47$) roughly halved the rate, and a fault-tolerant
auto-resume loop makes training unattended.
(5)~Zero dataloader workers starve the GPU ($\sim$20$\times$ slowdown); use \texttt{num\_workers}=4.
(6)~PyTorch 2.11's dynamo ONNX exporter fails on VITS spline flows; use the legacy exporter
(\texttt{dynamo=False}) and install \texttt{onnxscript}.
